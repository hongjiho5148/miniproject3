# 동시성 · 캐시 측정 결과

로컬 PC에서 직접 측정한 값입니다. (Spring Boot 단일 인스턴스 + Docker MySQL 8.0 + Docker Redis 7, 같은 머신)
절대값은 환경에 따라 달라지므로 **전/후 비교 용도**로만 해석해야 합니다.

재현 방법
```bash
node concurrency-test.js 50 20   # 라운드 50회, 동시 승인 20개
node cache-benchmark.js 60 100   # 사용자 60명 x 상품 9종 = 결제 540건, 케이스당 100회 조회
node sql-count-probe.js <백엔드 로그 경로> 5   # 조회 1회당 SELECT 수 확인
```

## 1. 동시성: 낙관적 락(`@Version`) 유무 비교 (50라운드)

| 시나리오 | 락 없음 | 락 있음 |
| --- | --- | --- |
| 승인 vs 취소 동시 요청 — 둘 다 성공(200) | 26 / 50 | 0 / 50 |
| 승인 vs 취소 — 최종 상태 불일치 | 26 / 50 | 0 / 50 |
| 승인 vs 만료 동시 요청 — 둘 다 성공(200) | 2 / 50 | 0 / 50 |
| 승인 vs 만료 — 최종 상태 불일치 | 1 / 50 | 0 / 50 |
| 같은 건에 승인 20개 동시 요청 — 라운드당 성공이 정확히 1건 | 50 / 50 | 50 / 50 |

해석
- 서로 다른 연산(승인/취소/만료)이 같은 결제 행을 동시에 바꾸는 경합에서 낙관적 락이 상태 불일치를 막았습니다.
- 같은 승인이 중복으로 들어오는 경우는 `payment_history`의 유니크 제약(거래 ID)이 이미 막고 있어서, 락 유무와 무관하게 1건만 성공했습니다. 즉 이 케이스에서 락의 추가 효과는 측정되지 않았습니다.
- 락 있는 상태에서도 동시 승인 20개 중 유니크 제약에 먼저 걸린 요청이 500으로 나가고 있었고(600건 중 270건), `DataIntegrityViolationException`을 409로 매핑해 0건으로 줄였습니다.
- 동시 충돌이 DB 데드락(`CannotAcquireLockException`)으로 나타나는 경우도 있어 `ConcurrencyFailureException` 기준으로 409 처리했습니다.

## 2. 조회 성능: Redis 캐시와 N+1 수정 (결제 540건, 케이스당 100회, 중앙값)

| 구성 | cache miss (DB 조회) | cache hit | miss 시 SELECT 수 |
| --- | --- | --- | --- |
| 수정 전 (N+1) | 814 ms | 16 ms | 결제 N건당 약 N+1+회원 수 (45건 조회 시 51개) |
| N+1 수정 후 (`@EntityGraph`) | 33 ms | 13 ms | 1개 (585건 조회 시) |

해석
- 캐시만 보면 50배(814 -> 16ms)로 보이지만, miss 경로가 N+1 때문에 느렸던 영향이 큽니다.
- N+1을 고치자 DB 조회 경로가 약 24배(814 -> 33ms) 빨라졌고, 그 위에 캐시가 추가로 약 2.6배(33 -> 13ms)를 줄였습니다.
- 응답 크기는 약 160KB(540건)이며, 같은 머신에서 측정해 네트워크 지연은 거의 포함되지 않았습니다.
